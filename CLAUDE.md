# CLAUDE.md — booblik

Брокер сообщений на Kotlin/JVM: append-only лог, сегменты, чтение по числовому оффсету.
Один процесс, без кластера. JDK 25, Gradle 9.6.1, Kotlin 2.4.10.

## С чего начинать сессию

1. [docs/research/research-architecture.md](docs/research/research-architecture.md) — решения
   и их обоснования. Без этого файла задачи выглядят как «сделай как в драфте», а драфт в двух
   центральных пунктах опровергнут:
   - **Kafka пишет лог не через mmap** — через `FileChannel`; mmap у неё только под индекс (§1.1).
     Поэтому здесь реализованы **обе** записи за одним интерфейсом, и выбирает их бенчмарк, а не
     цитата;
   - **публичный API Ktor Network не отдаёт `SocketChannel`** (§1.3) — то есть zero-copy через
     Ktor не сделать без каста к `Selectable`, который держится на внутреннем наследовании и
     ломается в рантайме. Отсюда решение писать сетевой слой самим;
   - **`value class` в generic-позиции боксится** (§1.6) — `ConcurrentSkipListMap<Offset, Position>`
     из драфта аллоцировал бы два бокса на сообщение ровно там, где обещан ноль аллокаций;
   - **FFM проверяет выравнивание**, а `MappedByteBuffer` не проверял (§1.7): нужен
     `JAVA_INT_UNALIGNED`, иначе падение на первой же невыровненной записи;
   - **бенчмарк-метод не может возвращать `value class`** (§1.8) — Kotlin манглит имя, генератор
     JMH отвергает;
   - **`msync` слабее `fsync` на macOS и равносилен на Linux — это про API, а не про ФС** (§1.9).
     На Linux `msync(MS_SYNC)` зовёт `vfs_fsync_range`, ту же функцию, что и `fsync`
     (`mm/msync.c:96`); на macOS `fsync` до пластин не доводит вовсе, нужен `F_FULLFSYNC`, и JDK
     зовёт именно его (`FileDispatcherImpl.c:51`), а `msync` — нет.
     `MappedSegmentWriter.force()` зовёт оба вызова: обязательно на macOS, почти бесплатно
     на Linux. Убрать второй — значит тихо ослабить `FORCED` на macOS;
   - **единица записи важнее пути записи** (риск 3) — но только наполовину: батчи дают 54 раза
     у обоих путей, а «полтора раза за путь записи» верно лишь для `FILE_CHANNEL`. Он перестаёт
     отвечать на рост батча (785 тыс против 809 тыс между 10 и 100), тогда как маппинг отвечает
     до 58,6×, и на настоящем ext4 разрыв доходит до 10 раз (замер 12.3);
   - **свой сетевой слой окупился транспортом, а не `sendfile`** (поправка к Р3): селектор
     обгоняет виртуальные потоки везде, а zero-copy не даёт ничего ниже гигабайта в секунду
     и отыгрывает только у насыщения;
   - **`transferTo` становится `sendfile` только для цели-`SocketChannel`** (§1.13), и все пути
     возвращают одинаковые байты — подмену не видно ничем, кроме графика.
2. [BACKLOG.md](BACKLOG.md) — что делать. Закрыты M0–M6, M-45 и **M-46**: умолчание `MAPPED`
   подтверждено на настоящем ext4, риск 1 закрыт, три вывода проекта отозваны (замер 12).
   Открыты **M-37** (стенд делит JVM и четыре ядра с брокером — теперь это мешает мерить),
   M-38 (нужна сеть от 10 Гбит/с, на 0,98 ГиБ/с неразрешима), M-64.
3. [docs/benchmarking.md](docs/benchmarking.md) — все снятые числа и правила, по которым их
   снимают.
4. Документ слоя, к которому относится задача: [docs/features/](docs/features/),
   [docs/api/](docs/api/), [docs/services/](docs/services/).

## Два правила проекта

> **Гейт — одна команда.**

```bash
./gradlew check
```

Тесты и ktlint во всех модулях. Плагин вешает `ktlintCheck` на `check`, поэтому обычный
`./gradlew build` прогоняет и его; отдельной строки в CI не нужно. Починить формат:

```bash
./gradlew ktlintFormat
```

Версия форматтера задана явно — `ktlint = "1.8.0"` в каталоге версий; плагин лишь запускает CLI
этой версии. Стиль и длина строки — в `.editorconfig` (`ktlint_official`, 120).

Две вещи ktlint не чинит сам: **KDoc перед выражением** (в `.kts` это частый случай — меняйте
на `/* */`) и **два KDoc подряд**.

> **Веха не закрывается без замера.**

```bash
./gradlew :booblik-benchmark:mainBenchmark
```

Профиль можно заменить целиком на один прогон — только чтобы ответить «во что обходится
профиль», и всё:

```bash
./gradlew :booblik-benchmark:mainBenchmark -Pbooblik.jvmArgs="-Xmx4G -XX:+UseG1GC"
```

Результат — строкой в [docs/benchmarking.md](docs/benchmarking.md): хост, режим сброса, число.
Веха, изменившая горячий путь и не показавшая цифру, считается незакрытой. Быстрая прикидка
за минуту — `mainQuickBenchmark`, но её числа **в отчёт не годятся**: доверительный интервал
там шире оценки.

Есть ещё четыре **пробы** — это не бенчмарки, и они отвечают на вопросы про форму, которую JMH
как раз усредняет:

```bash
./gradlew :booblik-benchmark:probeDurability
```

```bash
./gradlew :booblik-benchmark:probeStartup -Pargs="MAPPED"
```

```bash
./gradlew :booblik-benchmark:probeSustainedWrite -Pargs="MAPPED 60"
```

```bash
./gradlew :booblik-benchmark:probeLoad -Pargs="PRODUCE SELECTOR ZERO_COPY 8 20000 15"
```

Проверяют соответственно: что покупает `msync` (M-24), скорость восстановления (M-23),
пропускную способность на дистанции больше ОЗУ (M-26) и сквозной путь по сокету (M-33/M-34).
`probeSustainedWrite` удерживает лог retention'ом и **отказывается стартовать**, если на диске
мало места.

**`probeLoad` — открытый цикл.** Задержка считается от момента, когда запрос был *должен* уйти.
Не переделывайте его в «отправил — дождался»: такой стенд при замедлении брокера перестаёт
просить и рисует красивые перцентили (coordinated omission).

## Запустить брокер

```bash
./gradlew :booblik-app:run --args="booblik-app/broker.properties.example"
```

Проверить, что дистрибутив действительно стартует, обслуживает и переживает рестарт (это же
гоняет CI):

```bash
./ci/smoke.sh
```

Он не декорация: единственный настоящий баг M5 нашёлся именно так. Тесты поднимают сервер
из кода, поставку до этого не проверял никто.

**`booblik.flush.every.*` ограничивает окно потери, а не даёт долговечность.** Продюсеру,
которому ответили `WRITTEN`, ответили до всякого барьера. Ждёт барьера только `FORCED`.

## Профиль рантайма

Брокер живёт вот в этом, и это **ограничение**, а не настройка:

```
-XX:+UseSerialGC -XX:ReservedCodeCacheSize=32M -XX:MaxDirectMemorySize=32M
-Xss256k -XX:MaxMetaspaceSize=80M -Xmx64M
```

Задан один раз — `brokerJvmArgs` в корневом `build.gradle.kts` — и применён и к тестам, и к форку
бенчмарка. Правишь — правь там, а не в модуле.

Три следствия, каждое неочевидно:

* **Горячий путь не имеет права аллоцировать.** 64 МиБ кучи превращают это из пожелания
  в проверяемое свойство: тест, который начнёт мусорить, упадёт в гейте.
* **`-Xmx` не ограничивает маппинг.** Память от `FileChannel.map` — ни куча, ни direct-buffer,
  поэтому `MAPPED` адресует 512-мегабайтный сегмент внутри 64-мегабайтной кучи. Работает, но
  означает, что rss процесса эти флаги не ограничивают вовсе.
* **Профиль почти ничего не стоит** — замер 1 показал совпадение с умолчаниями JVM в семи строках
  из восьми. Это проверено, а не предположено.

Флаги доезжают до измеряемого процесса потому, что JMH передаёт форку аргументы хостовой JVM.
Это поведение JMH, а не наше, поэтому оно **проверяется**: `RuntimeFootprint` валит прогон, если
флагов нет, и печатает фактический список в шапке отчёта. Правило простое — если правишь
`brokerJvmArgs`, посмотри на эту строку в выводе.

## Что важно знать про замеры здесь

* **Число без режима сброса бессмысленно**, а не неточно. Без `force()` меряется page cache,
  с ним — диск, разница на текущем хосте — четыре порядка.
* **Короткий замер завышает mapped-путь в разы.** На маке 8,4 млн записей в секунду на свежем
  сегменте против 1,2 млн на минутной дистанции. Прежде чем радоваться числу из JMH, посмотрите
  на замер 3.
* **Стенды врут по-разному, и знать как — обязательно.** Мак — рабочий ноутбук с диском на
  94 % и load average около 2,5. «WSL2» — ext4 на виртуальном диске поверх NTFS, ядро Microsoft,
  память отдаётся хостом (§1.12); про долговечность он не свидетельствует вовсе, потому что
  дойдёт ли `fsync` до носителя, решает Hyper-V. **Арендованная машина (M-46, §1.15)** —
  ext4 на локальном диске с проверенно честными барьерами, и числа замера 12 сняты там; её
  оговорка одна — KVM, а не bare-metal, плюс всего 4 ядра, из-за чего сквозные замеры описывают
  пару «брокер + нагрузчик» (M-37). Осмысленны **относительные** сравнения внутри одного
  прогона — на них и построены выводы.
* **Для вопросов долговечности берите арендованную машину, в крайнем случае мак.** Там барьеры
  проверены `fio`, здесь `force()` — это хотя бы `F_FULLFSYNC`, про который известно, что он
  значит. WSL2 для этих вопросов не годится вовсе.
* **Проверьте, на чём лежит то, что меряете.** На Ubuntu 26.04 `/tmp` — tmpfs, то есть память,
  и `fsync` там no-op. Проба M-24 из-за этого отрапортовала барьер за 0,01 мс и напечатала
  уверенный вывод про `msync`; поймано в M-46 арифметикой (32 МиБ за 10 мкс — 3,2 ТБ/с). Теперь
  измеряющий код ходит через `MeasurementDir`, пишет в `build/measurements` и **отказывается**
  стартовать на летучей ФС, а носитель печатается в шапке пробы.
* Прогон на арендованной Linux-машине — одна команда:

```bash
BOOBLIK_REMOTE_HOST=root@адрес BOOBLIK_REMOTE_KEY=~/.ssh/ключ BOOBLIK_REMOTE_RAW=1 ./ci/remote-run.sh :booblik-benchmark:mainBenchmark
```

  Скрипт отказывается работать, если каталог прогона на сетевом хранилище: арендованный сервер
  с примонтированным Volume считает и собирает как обычный, а меряет сеть провайдера.
* Прогон на WSL — та же схема:

```bash
BOOBLIK_WSL_HOST=пользователь@адрес ./ci/wsl-run.sh :booblik-benchmark:mainBenchmark
```

  У неё своя ловушка, и скрипт её ловит сам: сессия WSL стартует в `/mnt/c/...`, дерево уезжает
  на 9p поверх NTFS, всё собирается и работает — а меряется не то.
* **Сравнивать прогоны с разных хостов нельзя.** ФС, writeback и JDK влияют больше, чем разница,
  которую обычно ищут. Это особенно касается соотношения `msync`/`fsync` — оно свойство ФС.
* **Прежде чем объяснять хвост свойствами брокера, проверьте измеритель.** В M3 стенд дважды
  выдавал правдоподобные числа, будучи неправ: спин на ожиданиях меньше 2 мс занимал все ядра
  машины (p99 110 мс вместо 16 мс), и полезная нагрузка аллоцировалась на каждый запрос.
* **Стенд живёт в одной JVM с брокером** и делит с ним 64 МиБ кучи (M-37). Счётчики GC печатаются
  рядом с перцентилями именно поэтому.
* **`probeSustainedWrite` подвешивает машину, на которой запущен** — насыщать writeback это его
  работа. На маке с 16 ГиБ и почти полным диском он сделал ноутбук неотзывчивым на минуту.
  Гоняйте там, где не работаете.
* **Числа из разных замеров этого документа несравнимы даже на одном хосте.** Показано в M-44:
  контрольный прогон той же конфигурации разошёлся с замером 8 на 37 % — другой день, тот же
  ноутбук. Сравнивайте только прогоны одной сессии, идущие подряд.

## Сборка

```bash
./gradlew build
```

Тулчейн — **JDK 25**, и это не «взяли посвежее»: на нём доступен FFM-маппинг
(`FileChannel.map(…, Arena)`) без потолка 2 ГБ и с детерминированным освобождением, вместо
`MappedByteBuffer`, который освобождается только сборщиком мусора (ресёрч §1.5).

## Структура

| Модуль | Про что |
|---|---|
| `:booblik-core` | хранение: сегмент, разреженный индекс, две реализации записи, `transferTo` |
| `:booblik-net` | провод: свой селектор, кодек, сессии, два транспорта, два пути FETCH |
| `:booblik-app` | запуск: конфигурация, метрики, retention, дистрибутив |
| `:booblik-benchmark` | числа: JMH через kotlinx-benchmark плюс четыре пробы |

## Язык

Код, KDoc и комментарии — **по-английски**. Документация в `docs/`, `BACKLOG.md` и этот файл —
**по-русски**. Репозиторий открытый; правило заведено до первого коммита, потому что переводить
потом дороже.

## Правило про документацию

> **`main` описывает то, что есть.**

Меняешь поведение, описанное в документе, — правь документ тем же коммитом. Проверяй утверждение
по источнику (исходник библиотеки, javadoc, прогон, артефакт в Maven Central), а не по соседнему
документу. В ресёрче прогоны, чтение исходников и гипотезы разделены намеренно — не смешивай их
при правке.
